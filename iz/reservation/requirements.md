# Етап 1. Вимоги підсистеми «Резервування»

Виконавець: Гладун Олександр.

## Призначення

Підсистема веде життєвий цикл резервування препарату: від створення покупцем до передачі в
підсистему «Продаж» для видачі. Вона утримує товар для покупця, контролює строк дії та повертає
залишок, якщо покупець не прийшов.

## Стейкхолдери

| Стейкхолдер | Інтерес |
|---|---|
| Покупець | бути певним, що препарат його дочекається, і мати змогу скасувати резерв |
| Фармацевт | бачити, що зібрати, і продовжити резерв на прохання покупця |
| Завідувач аптеки | товар не блокується без контролю строку |
| SMS-шлюз | отримує текст сповіщення |

## Межі

| Підсистема робить сама | Отримує від інших |
|---|---|
| створення, скасування, збирання, продовження та анулювання резервування | перевірку е-рецепта від підсистеми «Продаж» (UC9) |
| блокування й повернення залишку партії | видачу резерву виконує підсистема «Продаж» (UC6) через інтерфейс |
| сповіщення покупця про готовність | дані про партії надає спільний каталог |

## Вимоги

Вимоги позначено атрибутом `subsystem: Резервування` у файлі `lab1/srs.yaml`.

| ID | Вимога | Пріоритет |
|---|---|---|
| R2 | резервування препарату покупцем | 1 |
| R2.1 | не більше 3 активних резервувань | 1 |
| R2.2 | кількість від 1 до 6 упаковок | 1 |
| R2.3 | блокування залишку на час дії | 1 |
| R2.4 | чинний е-рецепт для рецептурного препарату | 2 |
| R2.5 | партія з найближчим строком, залишковий строк не менше 30 днів | 2 |
| R3 | скасування власного активного резервування | 2 |
| R3.1 | скасування лише тим, хто створив резервування | 1 |
| R3.2 | відновлення доступного залишку після скасування | 1 |
| R4 | анулювання не виданого за 24 години | 1 |
| R4.1 | повернення кількості анульованого резервування | 1 |
| R4.2 | одноразове продовження на 24 години | 3 |
| R12 | сповіщення про готовність | 3 |
| R12.1 | фіксація факту сповіщення, якщо шлюз недоступний | 3 |
| N7 | резервування не довше 3 с при 200 користувачах | 2 |
| N8 | анулювання не пізніше 5 хвилин після завершення строку | 2 |

Вимоги R3.1, R3.2, R12.1, N7 і N8 додано під час деталізації. Перевірка валідатором ЛР 1 збережена у
файлі `results/validate.txt`.
